# Windows 切号器刷新与资源优化总体架构

日期：2026-10-18。基线：Windows 1.0.6，提交 `7f005f4`。

## 目标与范围

用户要求先设计总体架构，再制定修改优化计划，最后实施、打包并推送 GitHub。用户已澄清：内存优化针对切号程序本身，并明确要求考虑生成数据的存储与定期清理。保留现有 Windows 10/11 x64、.NET 8 WinForms 界面和切号事务安全边界。

成功标准：额度一旦成功取得即可更新；手动刷新、切号后刷新不静默遗漏；后台减少无必要工作；查询进程、协议读取和历史明细有明确资源上界。资源收益必须用测量或明确的请求/并发数量说明，不承诺未经测量的降幅。

## 已确认的现状

- 当前实际入口是 `Program.cs` 的 `MainForm`，未启用旧托盘入口。
- 主窗口每 60 秒刷新全部账号。请求进行中时，后续刷新直接返回已有任务；切换账号后只重新读取本地状态。
- `CodexRpcClient.FetchUsageAsync` 先取得额度，再等待可选 Token 统计，最终才返回。Token 请求允许等待 5 秒，因此已取得的额度仍会延迟显示。
- 真实日志反复出现额度接口 8 秒超时、Token 接口 5 秒超时，以及网络请求失败。不能把这些归结为单一 UI 故障，也不能承诺本地优化消除服务延迟。
- 每个账号使用临时隔离 `CODEX_HOME` 和短生命周期 app-server。当前最多 3 个并发，单账号截止时间 20 秒；已有取消、进程树清理、凭据轮换和回滚保护。
- stdout 使用无限长 `ReadLineAsync`；Token 日明细和旧额度缓存没有明确长度上界。账号同步锁按历史账号 ID 保留。
- 日志无轮转；每次切号生成明文凭据备份且没有数量上限。现有临时清理只处理 `usage-*`，没有活动租约；`login-*` 崩溃遗留未定期处理。
- 登录临时目录目前在加密导入之前删除；导入失败需要重新登录。凭据轮换后进程崩溃与恢复标记写入之间也存在窗口，不能把所有旧临时目录视为垃圾。
- 单次运行快照：切号器工作集约 117 MiB、私有内存约 41 MiB。这不能证明泄漏。现有完整测试 286 项通过（Core 193、Integration 93）。

## 方案比较

1. **推荐：分阶段刷新 + 有限资源。** 保留现有进程隔离和安全逻辑；通过回调先发布额度，再补 Token。改动可控制，能验证刷新时序和资源边界。
2. 只缩短 Timer、增加并发：可能减少等待，却增加进程峰值、网络请求和电脑负担，且无法解决额度被 Token 拖延的问题。
3. 常驻每账号查询进程或直接调用未公开 HTTP 接口：可能减少启动成本，但会扩大凭据生命周期、协议维护和进程管理复杂度，本次不采用。

## 组件与数据流

### 1. UI 刷新调度

主窗口负责用户意图、可见状态和 UI 更新，Core 负责账号刷新与缓存。

- 正常窗口自动刷新间隔 60 秒，最小化时 300 秒；恢复后仅在数据已过期时补刷。
- 自动刷新若已有任务则合并；进行中的手动刷新请求最多保留一轮待执行，不创建无限队列。
- 切号完成先重新读取当前账号，再触发刷新，优先当前账号。账号/Provider 变更操作仍先取消并等待刷新清理。
- UI 刷新使用序列号阻止旧回调覆盖新状态；关闭时取消并等待已有任务，待执行请求作废。
- 普通后台刷新不清空已有数字；额度与 Token 各自保留真实取得时间。显示 Token 已有数据的读取时间，不能把缓存时间改成现在。

### 2. Core 刷新协调

- 保持同一轮只运行一个刷新任务，最大账号并发由 3 降为 2，并优先安排当前账号。
- 保留单账号 20 秒总截止时间、必需额度接口和可选 Token 接口的独立超时。
- 额度到达即发布 `UsageState.Available` 阶段快照，并沿用旧 Token 状态；可选请求完成后发布最终快照。
- 自动 Token 读取间隔 300 秒；缺少数据时首次读取，失败后也至少间隔 300 秒再自动尝试。手动刷新和切号后刷新可强制读取。
- 跳过 Token 请求保留原 Token 状态和原时间；Token 失败保留已取得额度和旧 Token 快照，显示失败原因。
- 已完成账号仍逐个落盘；取消仍保存已完成部分。阶段额度也必须在最终可选请求失败/取消时保留。

### 3. 隔离查询适配器

- 新接口显式传递 `IncludeTokens` 和额度阶段回调；原有两参数 fetch delegate 保留兼容适配。
- 一次账号刷新仍只启动一个 app-server，不为额度/统计各开进程。
- 生产 RPC 在额度响应到达时记录时间并通知上层；最终快照沿用该时间。
- `await using` 继续负责退出查询进程树，保留临时目录清理与失败恢复。
- 不修改活动 Codex 的刷新令牌所有权，不扩大日志或发布物中的敏感信息范围。

### 4. 内存与输入边界

- stdout 按块读取；单条 JSON-RPC 消息最大 1,048,576 个字符，超过即失败并保留旧显示。必须在完整字符串构建前限制长度。
- Token 明细按有效日去重，最多保留最近 366 个日期；服务返回的累计统计不重算、不截断，本月汇总仍使用已返回的有效记录。详情明确说明保留上限。
- 旧额度缓存文件最大 8 MiB；损坏或超限缓存作为可重建数据忽略，随后重新刷新。账号、凭据和配置不在此策略范围内。
- 保持 stderr 当前 8,192 字符上界。继续复用账号控件，删除账号时释放控件。
- 账号查询锁必须可以回收或采用固定数量的锁；不随删除/新增账号无限增长。
- 不使用强制 GC、清空 WorkingSet、定时重启 Codex 等方式制造表面指标。

### 5. 数据存储与生命周期

保持现有本地文件布局，不引入数据库或常驻清理进程。默认应用数据根目录为 `%LOCALAPPDATA%\CodexSwitch`，可由 `CODEX_SWITCH_DATA_HOME` 指定；Codex 根目录为 `%USERPROFILE%\.codex`，可由 `CODEX_HOME` 指定。环境变量只用于现有约定，不扩大清理范围。

| 数据类别 | 位置 | 保存方式与清理规则 |
| --- | --- | --- |
| 账号凭据 | 应用根目录 `accounts` | DPAPI CurrentUser 加密；只随用户明确删除账号而删除，不定期清理 |
| 账号索引与设置 | 应用根目录 `config.json` | 原子覆盖；不按年龄清理，不受缓存限额影响 |
| 额度与 Token 缓存 | 应用根目录 `cache.json` | 每账号仅最新快照，原子覆盖；读取前检查 8 MiB 上限；保留最多 366 个有效日明细；刷新时过滤已删除账号，不追加快照历史 |
| 查询与登录临时文件 | 应用根目录 `tmp/usage-*`、`tmp/login-*` | 正常完成/取消且凭据已妥善保存后立即重试清理；异常遗留仅在标有 `cleanup-ready`、满 1 小时且没有活动租约时清理；没有凭据文件的明确生成目录也可回收 |
| 凭据恢复数据 | 标有 `auth-recovery-required` 的隔离目录 | 不自动删除，不计入可直接回收项；记录需人工处理的数量，不在日志输出凭据内容 |
| 运行/异常日志 | 应用根目录 `logs` | 两类日志各保留当前文件及 3 个轮转文件，单文件 2 MiB，单条记录最大 8 KiB；旧轮转文件超过 14 天可清理；先脱敏再限长 |
| Provider 配置备份 | Codex 根目录 `provider-switcher/backups` | 保持既有最近 10 份规则；仅匹配程序自身的配置备份文件 |
| 切号凭据备份 | Codex 根目录 `provider-switcher/auth-backups` | 新事务只有在写入和账号元数据均验证成功后，才标记备份为可自动回收；这类备份保留最近 10 份，30 天以上可删除，但始终保留最新一份。未标记的旧备份、失败恢复备份一律保留 |
| 安装包与便携包 | 开发仓库 `artifacts` / 用户下载位置 | 不属于运行时自动清理范围；仅打包明确白名单文件，不打包应用数据 |

**维护调度：** 启动后后台执行一次，之后每 6 小时在没有登录/切号/刷新事务时执行；同一时间最多一个维护任务。临时目录扫描不再按每个账号反复执行。退出时取消维护，不延长 UI 关闭；锁定文件、权限失败等进入下轮重试，不能让清理故障覆盖登录/刷新结果。

**删除边界：** 清理器只接受上述已知根目录及严格生成文件名；执行前验证规范化绝对路径仍在指定根目录内。跳过符号链接/junction/reparse point，不遍历用户文档、项目、聊天历史或整个 `.codex`。使用活动文件租约保护正在登录或查询的临时目录；不能仅依据目录时间推断任务已结束。使用中的文件与恢复标记优先于年龄/配额规则。

**临时凭据状态：** 写入凭据前创建 `pending-credentials` 标记，整个查询/登录持有活动租约。只有确认刷新后的凭据已经安全保存到加密账号库、或确认没有需要保存的凭据后，才生成 `cleanup-ready`。登录目录的寿命覆盖加密导入，而不在读取登录结果后立即删除。无法保存时留下 `auth-recovery-required`，未知旧目录与崩溃留下的 pending 状态只报告，不自动删除。这样清理规则不会依赖“没有来得及写错误标记就一定安全”的假设。

**凭据备份保护：** 不改变现有回滚所依赖的字节备份格式；对新建备份目录显式施加当前用户私有 ACL。成功标记失败时保留备份、记录维护失败，不反转已成功的切号结果。恢复失败的备份从不生成可回收标记。

**恢复与可观察性：** 维护日志仅记录分类、清理数量、估算释放字节和失败数量；凭据、Token 和原始账号内容不写入。缓存损坏可重新取得；账号存储损坏应明确报错并保留原文件，不能当缓存处理。自动清理不对未知旧凭据备份推断安全性，因此这部分不承诺完全有界，需在说明中明确。

## 错误、竞态与兼容性

- 用户取消与单账号超时保持不同语义；不能把关闭/取消报告成完整成功。
- 部分额度成功后，Token 超时、异常或取消不能回退到旧额度。
- 刷新期间切号、删除账号、退出窗口时，旧回调不得恢复已删除状态或再启动进程。
- 保持已有缓存格式可读取，新增行为通过可选参数/兼容构造器接入。
- 不改账号切换、强制退出范围、备份和失败回滚语义。

## 验证与交付

1. 先增加可控 FakeCli/任务屏障测试，证明额度先于慢 Token 发布；不用公网耗时作为断言。
2. 覆盖 Token TTL/失败冷却/手动强刷、当前账号优先、并发上限、取消后的部分结果、单轮待刷新合并。
3. 覆盖超长/无换行 stdout、366 天上界、重复日期、缓存损坏/超限；验证当前月与累计统计不改变。
4. 在隔离目录验证日志轮转、过期临时目录、活动租约、恢复标记、路径越界/reparse point、成功备份回收与未知备份保留；清理失败不得改变业务结果。
5. 完整运行 Windows Core/Integration 测试；用隔离数据和假进程验证界面。真实工作中的 Codex 不作为强制切号实验对象。
6. 记录合成场景的请求数、峰值并发和多轮资源测量；诚实区分切号器本体内存与查询子进程峰值。
7. 版本更新为 1.0.7，构建自带运行时的安装包、便携 ZIP 与 SHA256SUMS，检查发布文件白名单及敏感文件排除。
8. 提交架构、实施计划、源码、测试和发布说明，推送现有 GitHub 仓库，并发布对应构建产物；核实远端提交和可下载资源。

## 边界

这里能够减少切号器的后台工作、瞬时进程数量及无界数据风险。当前约 41 MiB 的私有内存包含框架与界面开销，不预设必然大幅下降。网络不稳定时仍可能失败；本次提升的是可见结果时序、明确的刷新触发与资源控制。
