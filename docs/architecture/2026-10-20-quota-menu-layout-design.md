# macOS 账号菜单宽度与额度重置时刻设计

状态：用户已确认“具体时刻与倒计时同排”；2.3.5/build 14 已实现并安装，详见[验收与限制](../verification/2026-10-20-quota-menu-layout.md)。以下保留原设计依据。

## 目标与成功条件

用户截图中的账号区域没有铺满原生菜单可用宽度，五小时行的标签显示为省略号。用户希望减少中部右侧多余留白，并直接看到五小时额度在北京时间几点重置。用户要求依次设计、制定计划、最后新开任务实施。

采用原生菜单，保留账号区现有顺序和高度。主窗口的具体重置时刻与倒计时始终可见且同排；卡片、标题区、分隔线及悬停背景共用可伸缩宽度。继续使用北京时间与实时本机时钟。当前阶段不涉及 Windows、代理、电源、预热发送逻辑或公开发布。

## 已确认事实与推断

- UsageHeaderView、ProfileCardView、相应 NSHostingView 和账号分隔线分别固定290pt。
- UsageRow 的窗口名称列仅16pt，不能保证“5时”完整显示；截图的省略号与这一约束吻合。
- 原生菜单含完整预热日期和较长的刷新动作标题。Apple 文档说明，菜单宽度由自定义 view.frame 和其他菜单项共同决定，菜单项可以比 view 更宽。固定宽度可解释右侧未利用区域，但尚未现场测定具体是哪一项主导菜单宽度。
- `primaryResetAt` 是服务端 `resetsAt` 转为 Date 的结果，已存在于 snapshot；展示不需要新增请求，也不能通过“现在+5小时”替代。
- 当前基线3c2378c已统一macOS北京时间，并将可见显示时钟与连接状态刷新分离。分钟重绘不得重新混入网络探测。
- 原图含真实账号，仅保存在忽略的本地 artifacts，不能提交、嵌入文档或公开上传。

参考：Apple《Views in Menu Items》明确支持宽度 autoresizing，并说明菜单 tracking 期间不支持调整大小：
https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/MenuList/Articles/ViewsInMenuItems.html

## 选定方案

比较三种布局：

1. 同排放具体时刻与倒计时：信息直接可见，不增加四账号菜单总高度；采用，用户已确认。
2. 新增独立重置说明行：更醒目，但四个账号约增加48–56pt高度，不采用。
3. 只显示具体时刻、倒计时移到悬停：最紧凑，但降低现有倒计时可见性，不采用。

以下全部是合成示例，不代表截图账号的真实时刻：

`5小时  [额度进度条]  30%  20:31 重置 · 余4时21分`

主窗口时间列按需使用紧凑文字以适应宽度，但不省略具体时刻、跨日标识或缓存标识。周窗口保持原有倒计时，不额外添加一行。

## 宽度和布局规则

只保留一个布局策略 AccountMenuLayout：

| 值 | 设计值 |
| --- | --- |
| minimumContentWidth | 340pt |
| horizontalPadding | 每侧10pt |
| windowLabelWidth | 34pt |
| percentageWidth | 30pt |
| primaryTimeWidth | 144pt |
| rowSpacing | 4pt |
| minimumBarWidth | 100pt |

在340pt宽度下，内容区320pt＝34+100+30+144+3×4。更宽时把多余空间交给进度条。

- 标题区、卡片、分隔线和对应 host 使用同一初始宽度；SwiftUI 内层移除独立290pt硬锁，允许在父容器内横向铺满。
- 所有自定义菜单 host 启用 `.width` autoresizing；原生菜单保留自身边距。目标是填满菜单项分配的区域，不要求覆盖菜单外框圆角及系统边距。
- 可把 root minimumWidth 设为340pt，但不能将其误认为最大宽度。原生较长项进一步撑宽时，卡片应随之伸展。
- 宽度在菜单建立/打开前交给 AppKit 布局；禁止每次tick执行“读menu.size→写host.width→menu.update→再读宽度”的循环，也不在tracking期间手动调整菜单宽度。
- 悬停、点击背景和可点击区域随卡片完整宽度扩展；各卡的百分比列与时间列保持对齐。
- 现有账号名、套餐/credits、重置卡、Token汇总和记录截止信息保留，不通过隐藏现有数据来制造紧凑效果。
- 主窗口真实duration=300时显示“5小时”；其他duration按真实窗口命名；没有duration时显示“主窗口”，不能凭界面位置强称五小时。次窗口仍按现有真实duration显示。

## 重置时刻文案与数据边界

新增纯展示 QuotaResetPresentation，消费 `resetAt`、同一帧 `now` 和 quota 的缓存标记。所有时刻使用 BeijingTime；格式不依赖本机时区。

| 条件 | 主文字示例 | 紧凑文字示例 |
| --- | --- | --- |
| 新鲜、北京同日、未来 | 20:31 重置 · 余4时21分 | 20:31 · 4时21分 |
| 新鲜、北京次日、未来 | 明日00:31 重置 · 余4时21分 | 明日00:31 · 4时21分 |
| 其他日期、未来 | 10/23 00:31 重置 · 余2天4时 | 10/23 00:31 · 2天4时 |
| 缓存、未来 | 缓存20:31 · 余4时21分 | 缓存20:31 · 4时21分 |
| 不足一分钟 | 20:31 重置 · 不足1分 | 20:31 · 不足1分 |
| 没有resetAt | 重置时间未返回 | 同主文字 |
| 缓存且没有resetAt | 缓存·未返回重置时刻 | 同主文字 |
| resetAt等于或早于now | 20:31 已到 · 待刷新 | 20:31 · 待刷新 |
| 过期且非北京同日 | 10/19 20:31 · 待刷新 | 同主文字 |

缓存文案在次日/其他日期也保留“缓存”，紧凑形式同样保留日期与状态。过去的缓存样本仍保留“缓存”标记。跨年相邻日用“明日”；其他跨年日期在inline使用M/d，完整年份在help和accessibility中给出。

- 主文字放不下时使用明确的紧凑文字，可采用 ViewThatFits；必须单行、不能用省略号截断关键时刻，不进一步缩小现有时间字号9pt。
- 次窗口虽仍只显示倒计时，也使用同一个144pt时间列并右对齐，使进度条和百分比列与主窗口对齐。
- help及accessibility始终给出“服务器报告重置：yyyy年M月d日 HH:mm:ss（北京时间）”、缓存状态及完整剩余时长；缺失时说明服务端未返回；过去时刻说明等待新读数。
- Header第一行可以改为“OpenAI 额度与重置（北京时间）”，用现有行说明时间口径，不新增头部说明行。
- Quota缓存仅依据quota状态：available为当前已取得额度，stale/reloginNeeded携带的snapshot为缓存。Token接口单独失败不能把有效额度标成缓存。
- 不能凭该时间判断窗口已启动/预热成功，不能用resetAt减5小时生成真实启动时刻，也不能在时刻过去后写“已重置/已恢复”。
- 新snapshot到达时跟随服务端resetAt更新，不把某次报告锁定成永久固定值。

## 实时刷新与稳定性

沿用 VisibleTimeClock：菜单打开时本地重算，之后按分钟及本机校时/唤醒更新。一个可见刷新批次中的标题、两条额度行和时间文案使用同一个now。

异步数据刷新和本地tick只更新现有host/rootView与稳定的菜单项，不能因时间变化重建root或连接/Token子菜单。新文案只用单行，时间到期、缺失、缓存切换本身不改变卡片高度。保留既有默认模式连接状态timer；不得让展示tick调用refreshStatus或发起额度CLI、端口探测或模型请求。
